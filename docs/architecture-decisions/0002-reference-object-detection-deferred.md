# ADR-0002: Reference Object Detection отложен до v2.0

- **Дата:** 2026-05-09
- **Статус:** accepted
- **Авторы:** Андрей, Claude

## Контекст

ТЗ (§5.2, Phase 2 weight estimation) описывает уровень 2 — **Reference
Object Detection** на базе Faster R-CNN + MobileNetV3 (arxiv:2405.16478, 2024,
RMSE 6.3г). Это ML-модель, не API-вызов: требует обучения / готовых весов,
+2-4GB RAM на VPS, отдельный inference-сервис.

## Решение

На MVP (v1.0–v1.5) реализуется **только уровень 1 (Chain Menu Database)** и
**уровень 3 (Visual Range Estimate с эталонным объектом в кадре)**. Поле
`WeightEstimate.source = "reference_object"` зарезервировано в схеме, но
никогда не возвращается из MVP-кода.

Реализация Faster R-CNN — в v2.0 (после $50k MRR), отдельным сервисом или
через managed inference (HuggingFace Inference Endpoints).

## Альтернативы

1. **Реализовать сразу на MVP** — отвергнуто: +2-3 недели разработки, +€20-30/мес
   на хостинг inference, при этом impact на UX неочевиден (Visual Range
   Estimate тоже даёт приемлемое качество с подтверждением пользователя).
2. **Использовать только Visual Range Estimate без эталонного объекта** —
   отвергнуто: точность сильно падает без эталона. Эталонный объект в кадре —
   обязательный элемент UX, его попросим у пользователя в Vision Phase 2.
3. **Использовать готовое решение типа Foodvisor / Calorie Mama API** —
   отвергнуто: вендор-локин, нарушает принцип "только Anthropic".

## Последствия

**Плюсы:**
- Минус 2-3 недели на MVP.
- Минус €20-30/мес на hosting.
- Архитектурное место в схеме (`WeightEstimate.source`) уже зарезервировано.

**Минусы:**
- Заявленная в ТЗ точность RMSE 6.3г недоступна на MVP. Реальная
  погрешность будет 10-15% (Visual Range Estimate). Компенсируем UX:
  возвращаем диапазон, не точное число; всегда предлагаем подтвердить вес.
- Маркетинг до v2.0 не должен заявлять "5-8% точность весовой оценки".
